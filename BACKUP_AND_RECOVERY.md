# Backup and recovery

**Goal for discussion, not an SLA:** ≤24h logical-backup loss window, ≤4h service restoration for a small pilot. For financial records this may be too much loss: require managed PITR, set an approved shorter RPO, validate recovery and reconcile external records before accepting real data. A backup is not accepted until a restore is tested.

**Tooling:** `scripts/backup-db.sh [private-dir]` creates a PG custom-format dump, verifies archive TOC and finalizes a private file under `umask 077`. It **does not encrypt or upload it**. Use PG16-compatible `pg_dump`, `pg_restore`, `psql` and Node; an ignored secret-injected `DATABASE_URL`. URI parts passed via libpq env, not password on argv. Restrict process access. Never archive `.env`, raw keys, credentials or dumps in Git. Production: encrypt to controlled recipients/KMS before off-host transfer; restrict decrypt rights, version retention, record digest, byte count, timestamps and exit status (no row contents). Vault key escrow separate from dump is needed for encrypted mail/BYO key. Rotate and test recovery keys under two-person control.

**Isolated drill**
1. Pick approved backup + PostgreSQL major version; provision new **empty** database ending `_restore` on private network. No app traffic, external AI, mail worker or gateway attached; replays can deliver old codes/notifications.
2. Supply `RESTORE_DATABASE_URL` privately. `scripts/restore-db.sh /private/path/file.dump` verifies target name/empty relation catalog, streams restore in one transaction, without source owner/ACL or source DB name. Only restore trusted, integrity-checked dumps. Roles, settings, extensions, TLS, secrets and provider configuration require separate provisioning.
3. Compare row counts by tenant/entity, migration hashes, sum posted/debit/credit and open invoices, stock movements, file size/checksum sample, pending jobs, due times and entitlement cutoffs. Confirm owner/employee permissions and a few authorized reads on the restore. Disable external sends; revoked credentials/sessions can reappear if restoring older state. Revoke sessions/old codes and reconcile settlement/outbox before any approved cutover. Record duration vs agreed RTO/RPO and discrepancies.
4. Schedule automated backups, age alarm, monthly restore rehearsal; audit access. Proposed rotation 7 daily + 4 weekly; counsel and customers must approve data residency, holds, secure purge and deletion tombstones. Restores must reapply approved deletions before serving. Never overwrite production during a drill.

**Observed 2026-11-18:** private PG 16.15 synthetic DB; `pg_dump`/`pg_restore` 16.2. On the final 7-migration schema a new empty target restored; source = target on workspaces **4**, invoices **4**, gross ledger minor units **33,805,250** (non-net fixture checksum, including the browser-recorded payment), logged project minutes **105**, attendance minutes **45**, executions **3**, mail jobs **9**, journal **7**. Aggregate metrics output matched on source and restore. A retry into the now nonempty target was refused before restore. An earlier fixture before the browser-recorded collection totaled 33,795,250; compare each restore with its own source, not the previous run. The time-entry table is `project_time`. These small local checks do not prove encrypted off-site retention, data-loss tolerance or regional failover.

**Restoring the split-role installation:** the serving role deliberately cannot read the Drizzle journal. Don't run a full dump as the web user or broaden its rights. Use a reviewed backup role with complete read access (the non-superuser migration owner was used for the local drill). `--no-owner --no-acl` means source roles/grants won't be replayed. Have a DBA create a **new empty** `*_restore` target, with the migration role as target DB owner or equivalent rights to restore schemas/comments. Restrict public DB/schema access, grant runtime only `CONNECT` on the target DB and `USAGE` on `public`. If the cluster already has the roles, do **not** rerun the first-init role-creation script. Restore with `RESTORE_DATABASE_URL` for the migration role; run `npm run db:migrate -- --grant-runtime` with that target as its DSN, then switch to the restored **runtime** DSN for verification. Keep all transports/workers off. On an isolated loopback restore, `node tests/ops-rehearsal.mjs acl` is read-only. Check application-specific totals, not just successful SQL execution.

The split-role PG16.2 follow-up restored five synthetic workspaces (including the SMTP rehearsal). Metrics and sample counts matched the source, the restricted ACL probe passed, and a second restore to that nonempty target was refused. This still does not test off-site retention or PITR.
