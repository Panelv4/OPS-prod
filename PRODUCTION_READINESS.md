# OpsPilot release decision · 18 November 2026

**Decision: ready for local evaluation with fictional records. Not approved for real customer data, public deployment or paid launch.** The new checkout runs without the archive's shared accounts, request-time migrations or network font downloads. An agency owner can follow a client from project creation through a recorded collection in the browser. That last step changes a ledger; it does not collect money from a card or bank account.

| Intended use | Decision | Basis |
|---|---|---|
| Local demo / engineering evaluation | **GO, synthetic only** | Login-free disposable `/demo`, or a new isolated database with private mail delivery for the full workflow |
| Pilot with an agency's actual client or employee records | **NO-GO** | The disposable container gate passed. Hosted ingress/access, real sender, off-site recovery, privacy and independent review gates remain open |
| Sell subscriptions or announce a launch | **NO-GO** | Only `off` and `stripe_test` billing exist. No hosted provider rehearsal, authorized merchant, validated willingness to pay or founder sign-off |

## What was verified

Tests ran on this branch (`arena/2a99e11b-ops-prod`, archive baseline `ef0fdd3`), on Linux with Node **22.22.3**, npm **10.9.8**, PostgreSQL **16.15** and Chromium **153**. The initial release verification used a new loopback `*_test` database, a separately installed runtime with **production dependencies only**, and fictional identities. That baseline ran natively; the separate Linux Docker/CI rehearsal below tested the packaged services. [The original inventory](AUDIT.md) records why the ZIP's 20 passing test groups did not establish release readiness.

## Packaging follow-up · restricted runtime and mail round trip

Evidence for the two CI gates: [Docker job](https://github.com/Panelv4/OPS-prod/actions/runs/44255942009/job/134637524574) and [native verification job](https://github.com/Panelv4/OPS-prod/actions/runs/44255942009/job/134637524894) on `425a1b3efd39baaae2599c96949ee30c1356bd3c`. Gate/step conclusions were retrieved; the raw runner log archive was not downloaded in this sandbox. Runner annotations flag the v4 Actions runtime deprecation and the moving `ubuntu-latest` label; pin/review the release runner and image digests before a real rollout.

- **Addressed a concrete packaging problem:** the proposed Compose web/worker previously used the Postgres bootstrap superuser. The revised stack keeps admin, DDL and serving logins separate. A read-only catalog probe on native PG **16.2** confirmed the actual runtime had no elevated membership, schema creation, table ownership, journal access, `TRUNCATE`, session updates or audit edits. Migrations and explicit grants ran twice as a non-superuser migrator. First-init refused a reused bootstrap password and refused to adopt existing roles. No change to the seven journaled migrations.
- **Native run with those privileges:** clean install, lint, typecheck and **44/44** build; `next start` from a separate **118-package production-only install**. All **28 HTTP/domain groups, 6 integration groups and 4 Chromium checkpoints** passed with the restricted login. These results are additional to the earlier PG16.15 baseline above.
- **End-to-end local mail:** on a clean synthetic DB, a signup queued verification between two separate worker processes. The restarted worker delivered it over SMTP to a real **loopback sink**; the captured code unlocked the web account and enabled a CRM import. The job recorded one successful attempt and discarded its payload. Reading auth codes out of the DB was not part of this gate. This was not the Mailpit container, an internet inbox or a real customer signup.
- **Role-aware restore:** separate empty `*_restore` DB, restored **as the migrator**, grants reapplied, read-only ACL probe passed as runtime. Source/restore metrics matched (5 fixture workspaces including mail rehearsal, 33,805,250 gross ledger minor units, 105 project minutes). No worker was attached to the restore. See [recovery](BACKUP_AND_RECOVERY.md) for credential and ownership requirements.

## Repeat on your own disposable data

Start at [environment setup](ENVIRONMENT_SETUP.md). Use an empty loopback `*_test` DB, unique random vault key, local origin and a Chromium binary. Export the test environment to both shells. Keep billing off, external AI off and real SMTP credentials absent. **Never run the fixture suite against a shared, staging-customer or production database.**

1. Install with `npm ci`; run `npm run lint` and `npm run typecheck`. Build in a clean build environment (no secret-bearing `.env`): `env -u DATABASE_URL -u OPSPILOT_SECRET_KEY NEXT_TELEMETRY_DISABLED=1 npm run build`.
2. In a separate one-shot migration-owner environment, run `npm run db:migrate -- --grant-runtime` twice on the initialized split-role DB. Then use the runtime-only fixture environment. Do **not** seed. To exercise a production-only package on the host, copy the built `.next/`, `src/`, `drizzle/`, `scripts/`, `public/`, manifests/lock, `tsconfig.json` and `next.config.mjs` to an isolated directory, install there with `npm ci --omit=dev`, and run the migrator/server/worker there. Keep dev dependencies in the test-runner checkout.
3. Start `npm run start -- -H 127.0.0.1 -p 3000` with `APP_ORIGIN` and `TEST_BASE_URL` matching that loopback URL. Check `/api/health`. With **no continuous worker** draining the fixture mailbox, run `npm test` and `CHROMIUM_PATH=/path/to/chromium npm run test:browser` from the test-runner checkout. The suite creates its own records; start fresh for independent results.
4. Run `npm run worker -- --once`, `npm run metrics`, then [restore to a different empty `*_restore` database](BACKUP_AND_RECOVERY.md). Compare counts, ledger totals and the metrics report. Never attach an outbound sender to a restored fixture. Check both audit scopes separately; don't suppress the full audit result.

## Gates still open — and who should close them

| Gate | Proposed owner | Evidence required before approval |
|---|---|---|
| Deployment and security | Engineering founder + independent reviewer | Keep container/CI green for the exact release revision; verify actual managed-environment roles and network restrictions; trusted ingress/TLS and body limits; tenant/custom-role review, synthetic load and worker soak. Patch or explicitly disposition tooling advisories. Rehearse a legacy migration separately **if migrating existing data** |
| Sender and recovery | Engineering + operations | Verify sending domain, bounce handling and recovery/invite delivery to an approved test mailbox. Alert on oldest queued jobs. Restore an encrypted off-site copy and escrowed keys; exercise PITR, holds/deletions, incident notification and rollback without resending mail |
| Commercial settlement | Merchant owner + engineering | Approved **test** account; hosted checkout and portal, signed actual sandbox events, reconciliation against the provider for failed renewals, plan changes, out-of-order refunds/disputes and cancellation. Live mode would need additional design, review and explicit financial authorization; it is not an env flag here |
| Privacy and support | Operations + qualified counsel | Confirm operator, contacts, vendors, locations/transfers, applicable law, retention and support hours. Rehearse scoped export/purge including multi-workspace users, audit and backup constraints. Approve [privacy procedures](PRIVACY_AND_DATA.md), [DPA/payment drafts](DPA_DRAFT.md) and a real-data handling policy |
| Demand and release decision | Both founders | Approve any outreach first. Seek 10 opt-in interviews; require the same handoff problem from 3 independent teams and 2 volunteers to repeat with a colleague before a synthetic pilot. Measure actual repeat use and cost; don't count compliments or test payments. Record owners, evidence, scope, budget, rollback and a dated go/no-go before expanding access |

**Next engineering handoff:** measure queue age, database connection use and worker recovery under sustained synthetic load. Keep the [Compose rehearsal](DEPLOYMENT_RUNBOOK.md) as a regression gate. Hosted staging, off-site recovery and a real sender test need a separate authorized environment. **First product decision:** approve or decline synthetic-data discovery with small web/design agencies, not a paid launch.
