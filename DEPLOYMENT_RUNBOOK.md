# Deployment runbook · rehearsal first, public rollout requires approval

## Disposable container gate

On a **Docker-enabled Linux host** with a local Unix-socket context, Compose v2 with `up --wait`, Bash, OpenSSL and curl, run from the repo root:

```sh
bash scripts/rehearse-compose.sh   # also: npm run test:compose
```

No `.env`, provider keys, pre-existing database or host Node install is needed for the Bash entry point. It builds the runtime image, pulls the specified PG and Mailpit images if missing, generates private one-use credentials and uses a random Compose project with new storage and dynamically assigned loopback ports. It refuses remote Docker contexts. It removes **only its disposable project's** containers/volume and tagged app image, including on failure. It does not prune the daemon. Do not send `docker inspect`, expanded Compose config or mailbox contents in a test report.

A passing run must observe: successful one-shot migration and repeat; host `/api/health`; non-root web and worker using the restricted DB login; a synthetic signup while the worker is **stopped** that cannot yet use the dashboard; verification delivered to the expected **Mailpit** recipient after restart; code accepted by the web API, scrubbed outbox row and one CRM import with billing off. These checks run via the [packaging probe](tests/ops-rehearsal.mjs), not by reading codes from SQL. CI's `container` job uses this same command. Record the checked revision, job URL, exit status and which stage failed/passed. A missing Docker prerequisite is a nonzero **not run**, not a pass. **First successful remote rehearsal:** [Actions run 44255942009](https://github.com/Panelv4/OPS-prod/actions/runs/44255942009), revision `425a1b3`. [Verification details and open gates](PRODUCTION_READINESS.md).

For an **interactive** local stack instead: make a private `.env.compose` from `.env.compose.example` (four independent random hex secrets), use a fresh project name, and run `docker compose -p opspilot-local --env-file .env.compose build app` then `docker compose -p opspilot-local --env-file .env.compose up -d --no-build`. Defaults: app `http://localhost:3000`, private mail UI `http://localhost:8025`, no published PG/SMTP port. `down` **without `-v`** preserves this stack's data. The PG image runs `scripts/postgres/init-roles.sql` only on an empty volume. Merely changing environment variables will **not** change stored passwords or convert an old one-login volume. Never drop it to get a green rehearsal; choose a new project and keep the old volume offline for a reviewed migration.

## Staged release (not authorized by a passing test)

1. **Go/no-go:** engineering records release revision, clean install/build/audits/tests/browser and container result; operations checks sender, recovery, support, legal drafts and cost alerts. Both sign off scope, region, budget and rollback owner. Stop if a critical gate is unmet. No live billing switch exists.
2. **Role preflight:** keep the bootstrap/admin credential out of the web, worker and migrator. Use `opspilot_migrator` for one-shot DDL and `opspilot_runtime` for both serving processes. `npm run db:migrate -- --grant-runtime` applies the journal, then explicit table grants while the migrator lock is held. If either part fails, don't start the app. A newly added table/action needs a grant review; do not grant schema ownership to fix a permission error. These credentials describe the local stack; re-provision and verify least privilege on the chosen managed service.
3. **DB preflight:** separate new DBs for test/staging/production; inspect current schema, migration hashes and table ownership. Migrator locks the physical session, rejects unjournaled existing tenants/mismatched journal or known seed slugs in production. Do not bless a legacy DB by inserting fake journal records. Rehearse on an isolated restore first. Audit duplicate keys, orphan children and tenant mismatches (join on both tenant and parent ID); review old invites/sessions, paid plans without settlement, shared seed identities, legacy AI/audit visibility, file sizes and secret custody. `0001` deliberately clears old plaintext invite codes. Document counts and authorized remediation, don't delete business rows to get green migrations. New composite constraints may correctly refuse bad legacy data.
4. **Provision only after approval:** private DB/network, runtime and migration roles, encrypted off-site backup/restore target, domain/TLS, secret manager, vetted SMTP sender & monitoring. Set canonical origin; verify TLS to DB and SMTP. Never use local catcher or `_demo` DB. Same build image for worker/web; pin and scan deploy image by digest. Stage uses different secrets, origin and resources, billing off unless this is the approved sandbox rehearsal.
5. **Release:** take pre-migration backup and verify readability. Run the reviewed migrations and applicable runtime grants as the one-shot migrator; rerun safely. Start worker and web under least privilege; inspect readiness, job age, and config. Register a synthetic operator tenant and run authorized smoke checks, not the destructive fixture test suite against a live DB. Confirm anonymous API denials, cookie flags, HTTPS-only redirects, no secret values in logs, restricted staff dashboard, queue delivery and recovery. Scope first pilot to one consenting agency with verified operator support.
6. **Sandbox-only billing rehearsal:** distinct customer/test catalog, API version `2025-02-24.acacia`; endpoint `/api/billing/webhook`, subscribe to `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, `charge.dispute.created`. Verify raw signature/tolerance, paid invoice & captured charge, owner mapping and correct term. Test customer abandonment, replay, switch with no proration, price mismatch, failed renewal, expiry, partial/full refund, dispute and cancellation. Reconcile historical invoices vs provider dashboard; do not replay arbitrary events as “paid”. Return from Checkout without a webhook must not change entitlements. Test hosted links are missing evidence today.
7. **Roll back:** if schema is compatible, pause new writes/jobs, redeploy known compatible image, restore worker then verify health/ledger/jobs. If not compatible, **do not run ad hoc down SQL**: preserve failing DB, create isolated restore/PITR target, reconcile post-backup writes and external settlement/mail before any cutover. Switching DSN, DNS, deleting records or contacting customers needs founder approval. Keep a decision log free of personal data, and a time budget for rollback.
