# Privacy notice and data operations · internal draft for counsel

**Not published, not a compliance claim.** Do not onboard real clients or employees with this draft. Fill and verify legal operator name, postal address, privacy/security contacts, representative/DPO if required, countries, vendors, lawful bases, retention periods, transfer safeguards and rights contact/complaint channels. Obtain qualified review in launch jurisdictions and founder approval. Do not assume the MIT code license provides a privacy notice, SaaS contract or DPA.

## Proposed plain-language notice

**Who controls what.** The proposed operator would decide how to process account identity, security, billing relationship and support records to run the service. A customer generally determines the purposes and permissions for its own workspace (e.g., its clients, employees and invoices); OpsPilot would process that content on its instructions. Confirm controller/processor roles for each purpose with counsel; do not call all data “ours”. The customer must be entitled to upload and manage its data and inform affected people. Not a service for children, payment-card storage or sensitive regulated records in a pilot.

### Cookies / browser storage inventory

`opspilot_session`: first-party login credential; HttpOnly, SameSite=Lax, Secure in production, absolute 14-day expiry; logout expires it. Per-session CSRF value is intentionally readable in JS memory and returned to authenticated client. `opspilot-theme` in localStorage remembers light/dark until cleared. Demo UI state is in tab memory; theme preference is separate. No ad pixels or third-party fonts in candidate code. A hosted payment page would be a separate provider context. Re-inventory deployed ingress/provider cookies and optional SDKs. Explain essential security storage, offer control over optional preferences, obtain prior consent where required before adding nonessential tracking; UK guidance distinguishes strictly necessary storage. [1](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guide-to-pecr/cookies-and-similar-technologies/)

### Retention and deletion: current behavior vs proposed policy

| Class | Implemented | Proposed human decision / outstanding work |
|---|---|---|
| Session / recovery / verification / invitation | Sessions expire in 14 days and are cleaned by worker. Recovery code 30m; verification 24h; invites 7d. Request claim checks expiry; stored hashes/rows can outlive validity | Remove expired/revoked hashes/obsolete membership invites after policy window; deal with abandoned signup. Invalidation ≠ erasure |
| Rate rows / mail delivery | Expired windows cleaned. Worker clears terminal or expired mail payload; finished mail job metadata eligible for deletion after 30d | Validate cleanup/oldest age, relay retention, bounce handling and backup expiry |
| CRM/HR/financial/files / audit | Persisted while workspace exists. File deletion removes versions by FK; normal audit rows protected from edit/delete | Customer- and jurisdiction-specific retention/holds; proposed 30-day export opportunity on closure, then scoped verified purge. No automated whole-workspace purge, no blanket auto-delete of payroll/audit. Must resolve audit FK/retention constraints before pilot |
| AI history, workflow payloads, usage, gateway history | Retained in DB; AI scope restricts reads, not physical deletion. History can contain user-entered text | Propose short operational input retention (e.g., 30d terminal payloads), minimum billing/audit metadata by need, aggregate usage review after 90d; implement and test before promising deadlines |
| Backups and support | Local restore validated, no verified offsite policy | Proposed 7 daily + 4 weekly encrypted copies subject to review. Tombstone/reapply approved erasures on restore. Publish actual provider retention and holds |

### Rights / export / closure procedure (operator-assisted proposal, not present self-service)

1. Offer a monitored privacy channel **before launch**. Log request ID, scope (individual or workspace), receipt/deadline by jurisdiction, role and owner. Verify identity/authority by a signed-in flow or existing verified business contact; don't ask for passwords, raw tokens or unnecessary IDs.
2. Identify controller for workspace records. Route a processor request to that customer, assist only on documented instructions; keep account-controller request separate. Check retention duty, legal hold, other tenants and third-party rights. If there is a conflict, escalate; never claim “we erased everything” because login was disabled.
3. On approved **export**, run against isolated authorized scope with read-only access. Select whitelisted business fields by tenant/member and subject; extract linked document versions only if entitled; redact other people's HR/finance, audit entries not shareable, password digests, sessions, tokens, keys, internal provider IDs and outbox payloads. Do not send a database dump. Produce CSV/JSON + manifest, counts and timestamps; neutralize spreadsheet formula interpretation on CSV export. Second reviewer samples contents, authorizes encrypted/expiring delivery to verified recipient; record download/expiry without contents. Self-service export is not implemented.
4. On **correction/deletion/closure**, confirm irreversible operation, distinguish one person's removal vs whole customer (users may belong to multiple tenants); export if requested; suspend access, revoke sessions, stop jobs/optional egress, reconcile eligible provider records. Two-person scope and approval, counsel-vetted deletion/anonymization sequence including files/versions, derived AI/workflow data, indexes, backups and subprocessors. Preserve minimum lawful finance/audit evidence separately with restricted access; don't disable immutable audit safeguards ad hoc. Verify counts + sample negative reads, log completion/exception and backup expiry. Deletion and notification outside fixtures require explicit approval. Implement and rehearse this tooling before real customer data.
5. Respond securely within applicable timelines, document reason if something cannot be deleted/returned, escalation/appeal and supervisory authority as applicable. Customer-facing SLA/contact and identities remain blanks pending review.
